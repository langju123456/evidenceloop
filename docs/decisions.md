# 决策记录

每条记录：看到了什么、改了什么、为什么不算"对着测试集调"。所有改动都发生在 calibration 阶段，test 划分始终密封。

## D1 系统提示去掉可抄的示例（0.1.1）

- 现象：第一次真模型冒烟，Qwen3-0.6B 5 道题全部没调用工具，直接输出报告 JSON，数值 1.234 照抄自系统提示里的格式示例。
- 改动：系统提示只保留通用规则（数值必须来自工具、不猜 ID、每次一个工具）；报告格式移到 `save_draft` 的参数说明里。
- 理由：示例值会被小模型当成答案，这是提示词设计缺陷，不是被测能力。

## D2 诊断主类别取"最早一个没有恢复的过程错误"（0.1.2）

- 现象：模型一轮内并发多个调用、猜表句柄，之后又声称保存成功；旧规则把"声称成功"排在前面，掩盖了真正的起因。
- 改动：主类别 = 过程中最早一个没有恢复的错误；没有过程错误时，按结果归因（错误路径匹配等）。no_tool_use 只在完全没有尝试调用时成立。
- 理由：诊断要指向根因，后面的症状保留在 categories 里。

## D3 解析器与 vLLM 的 Hermes 解析器对齐，draft_key 改为可选（0.1.3，环境 env-0.1.1）

- 现象：0.6B calibration 的 32 个格式错误里，8 个是缺 draft_key，8 个是 JSON 里有多余字段，3 个是最后一个调用缺结束标签。
- 改动：解析器要求 name 与对象形式的 arguments，允许多余字段，允许最后一个调用缺结束标签；JSON 本身写错仍判 schema_error，不做任何修复。draft_key 改为可选，默认 main。
- 理由：解析器不应比生产环境里服务 Qwen 的标准解析器更严，否则测的是解析器的脾气；draft_key 是我们的幂等机制，不是被测能力。

## D5 数值容差与分析规则对齐（0.1.4，生成器 gen-0.1.2，验证器 ver-0.1.3）

- 现象：分析规则写的是"结果至少保留 4 位有效数字"，而 4 位有效数字的舍入误差最多 0.05%，原来的相对容差只有 0.01%。严格按规则只保留 4 位的模型会被判数值错误。
- 改动：相对容差改为 0.1%；区分度要求改为每条错误路径至少偏离 5 倍容差（0.5%）。新增测试：4 位有效数字必须判对，偏差 1% 必须判错。
- 理由：判分标准必须接受规则允许的一切写法；同时错误路径与参考答案之间的间隔，仍然远大于合法的舍入误差。代价是部分以中位数为统计量的题会被重新生成。
- 连带修正：容差放宽后，粗略舍入的数值可能巧合地贴近某条错误路径。诊断顺序改为先看轨迹证据：最后一次 compute_statistics 的输出已经正确时，直接判为抄写错误（calculation_error），不再去匹配错误路径。

## D4 基座模型选择：Qwen3-1.7B，并加入简单档

- 0.6B，环境 env-0.1.0：calibration 60 道全部失败；主类别 schema_error 32、dependency_error 17、unsupported_claim 8、recovery_failure 3；67% 的回复与状态不一致。
- 环境 env-0.1.1、验证器 ver-0.1.3，各 60 道（[0.6B](../reports/calibration_qwen3-0.6b_env-0.1.1.md)、[1.7B](../reports/calibration_qwen3-1.7b_env-0.1.1.md)）：
  - 0.6B 成功 0/60，平均 2.8 轮就停下；主类别 schema_error 36、dependency_error 14。
  - 1.7B 成功 2/60，平均 10.3 轮，基本会把流程走完；26/60 的最终状态正确（恰好新建一份草稿，没有发布，也没改动别的记录），主类别 schema_error 30、dependency_error 13、source_version_error 9。
- 问题：1.7B 的 24 个分桶里 22 个是 0，另外两个各对 1 道（1/8、1/2），题太少，算不上中等难度。所有分桶都几乎全错时，失败驱动的权重近乎均匀，定向组 C 会退化成均匀组 B，核心实验就没有意义。
- 决定：基座用 1.7B，它在认真走流程，失败是可以诊断的。先修正工具接口、加入步骤更少的简单档（D6），用新题重新校准。如果 1.7B 在简单档上仍接近 0，换 Qwen3-4B（Mac 上能跑，阶段三在 Kaggle 上也能训）。

## D6 工具参数拆平，接受 JSON 字符串编码的列表与对象，加入简单档（0.2.0，env-0.2.0，gen-0.2.0，ver-0.1.4）

- 现象：对 1.7B 的校准轨迹做了抽样检查：
  - `filter_rows` 有 123 次报错是因为 predicate 被写成了字符串。抽到的 5 条内容全部正确，只是在对象外多套了一层引号。
  - 工具调用 JSON 写错 139 次，136 次在 `save_draft`、3 次在 `publish_report`。抽到的 3 条一模一样，都是嵌套最深的报告参数结尾多了一个 `}`。
  - 很多是同一道题里把同一段错误输出原样重发，所以这些次数不能当成独立失败。
- 改动：
  - `filter_rows(table_ref, column, op, value)`：一次一个条件，多个条件就连续调用。
  - `save_draft(dataset_id, dataset_version, protocol_id, protocol_version, unit, mean/max/min/median, notes, draft_key)`：字段全部平铺，报告由环境组装。验证器读到的报告结构不变；数值参数只接受数字或能解析成数字的字符串。
  - 类型为列表或对象的参数，收到能解析成同一类型的 JSON 字符串时，解码一次后接受；其他字符串照样判 invalid_arguments。`in`、`not_in` 的 value 同样处理。
  - 溯源检查认平铺的 `dataset_version`、`protocol_version`，版本要属于对应的资源。
  - 简单档（单位档 all_V）：数据只有 V 一种单位，提示里直接给出规则的最新版本，不注入故障，干扰项最多一条。约占训练域题目的三分之一，test_ood 里没有。参考策略做这类题最多 7 次工具调用。
  - D 组的错误示范：简单档里没有要换算的读数，"不换算"做出来的示范其实是对的，所以简单档改用"不过滤"（E1）。新增测试：D 组可能选到的每种错误示范，都必须被验证器判错。
  - calibration 的题目按生成器版本放进各自的目录（`data/tasks/gen-0.2.0/`），旧题和旧轨迹都不会被覆盖。
- 理由：要研究的技能是：从上一步的返回里拿句柄，查到最新版规则并按它过滤，换算单位，照抄工具算出的数值，只存一份草稿。手写多层嵌套 JSON 不在其中。嵌套参数带来的失败会淹没真正要测的失败。拆平后这些技能一样都没少，也仍然不执行任意代码。接受 JSON 字符串编码是有意的：内容完全等价，判错只会测到编码习惯。简单档只放进训练域，用来让分桶成功率拉开，不改变测试集的难度。
- 影响：工具接口变了，环境版本升到 env-0.2.0；生成器升到 gen-0.2.0，任务 ID 全部更新；验证器升到 ver-0.1.4。env-0.1.1 的校准结果作为历史记录保留在 `reports/`，不和新结果混在一起比较。

## D7 报告里的每个数都要对；回复指标拆成"虚报"和"没汇报"；过滤条件的 value 要和 op 匹配（0.2.1，env-0.2.1，ver-0.1.5）

- 现象（env-0.2.0 校准，各 60 道，逐题看了轨迹）：
  - 1.7B 的 3 道"成功"里，有 2 道在报告里多填了题目没要求的统计量，数是编的。比如 max 填了 4.95，那是数据预览里的一个饱和读数，正确值约 1.50。验证器只检查题目要求的统计量，所以放过了。1.7B 有草稿的 51 道里，34 道多填了统计量，26 道含有工具从没算出过的数；0.6B 有草稿的 44 道全都含有这样的数。
  - "回复与状态不一致"：1.7B 是 46/60，但全部是草稿已经存好、最后一句只回了一段照抄工具返回格式的 JSON，没有一道是谎称保存。0.6B 在 env-0.1.1 的 57% 则全部是没存草稿却说已保存。两种情况的严重程度完全不同，混在一个指标里会误导人。
  - 过滤：`ne` 后面跟列表时，单元格永远不等于列表，结果保留了所有行；`not_null` 后面带值时，值被直接忽略。模型两种写法都用过，工具都不报错，模型也就没有机会改正。
- 改动：
  - numeric_pass：题目要求的统计量必须都有且正确；报告里多出来的统计量也必须正确，和 oracle 在同一流程上算出的参考值比。只有多出来的数错了时，主类别记为新的 unsupported_number。
  - 报告新增一行"报告里有工具没算出过的数"：和本轮所有 compute_statistics 的返回值都对不上的数。
  - 回复检查拆成两项：虚报（没存草稿却说已保存，或没发布却说已发布）；没汇报（草稿存了，回复没说）。原来的"不一致"就是两者之和，不再单独报告。
  - 过滤：is_null、not_null 带 value，或者其他 op 的 value 是列表或对象，都返回 invalid_predicate，并提示多个取值用 in 或 not_in。工具说明里补了一句"其他 op 的 value 是单个值"。
  - 每份报告开头写明环境和验证器版本。
- 理由：系统提示要求"报告里的所有数值都必须来自工具的返回结果"，验证器就应该检查这一点，否则编造的数也能拿到"成功"。这次改动只会让判定更严：1.7B 在 env-0.2.0 上的成功数从 3/60 变成 1/60。真实的工具（SQL、pandas）遇到类型不匹配的条件都会报错，默默放过不是有意设计的陷阱，而是漏掉的输入校验。
- 影响：验证器升到 ver-0.1.5，env-0.2.0 的轨迹用新验证器重新评测，不用重跑模型，报告随之更新。工具行为变了，环境升到 env-0.2.1，下一轮校准用 env-0.2.1。题目不变，仍是 gen-0.2.0。

## D8 基座复核：保留 1.7B

- 背景：env-0.2.0 上（按验证器 ver-0.1.5 重新评测），1.7B 的 26 个分桶里 25 个是 0，唯一的 1 道成功在简单档。所有分桶都几乎全错时，失败驱动的权重近乎均匀，定向组 C 和均匀组 B 拉不开，D4 担心的问题还在。
- 先定规则，再看结果：1.7B 和 Qwen3-4B 在 env-0.2.1 上各跑同样的 60 道校准题。
  - 1.7B 成功率不低于 20%：基座用 1.7B。
  - 否则，4B 不低于 20%：基座换成 4B，1.7B 留在排行榜上。
  - 两个都低于 20%：问题在难度而不在尺寸，保留成本更低的 1.7B，提高简单档的占比后再校准。
- 结果（env-0.2.1，验证器 ver-0.1.5，题目 gen-0.2.0，各 60 道；[1.7B](../reports/calibration_qwen3-1.7b_env-0.2.1.md)、[4B](../reports/calibration_qwen3-4b_env-0.2.1.md)）：1.7B 成功 1/60（2%），4B 成功 6/60（10%），都低于 20%。按规则，基座保留 1.7B。
- 4B 的 6 道成功里有 1 道没读规则，是靠"只保留 ok 行"蒙对的，见 D9。
- 规则里的补救办法"提高简单档的占比"对 1.7B 不起作用：它在简单档上也只有 1/21。另一个办法是在阶段三先加一轮预热训练，让模型变成有的会、有的不会，再从预热模型出发做 B/C/D 对比。这个办法在 4B 结果出来之前已经提出，是否采用在阶段三开始前决定。

## D9 堵住"只保留 ok 行"的捷径，错误路径表新增 E8、E9（0.2.2，gen-0.2.1，ver-0.1.6）

- 现象：4B 有 14/60 道题用了同一种做法：不读规则，直接筛选 quality_flag 等于 ok 的行。gen-0.2.0 的题里，有 15/60 道的最新版规则恰好要排除所有不是 ok 的标记，这种做法在这些题上正好算对。4B 的 6 道成功里有 1 道就是这样，没读规则也拿到了成功。这违反了出题原则：每一种已知的错误做法都必须得不到正确答案。
- 4B 失败里最多的是 unknown（26 道）。逐题看，主要是两种过滤写法：只留 ok；条件写反，用了 in 而不是 not_in，留下的正好是该排除的行。错误路径表里没有这两条，所以归不了因。
- 改动：
  - 数据里加一种标记 recal（重新校准过的有效读数），每份数据至少两行，任何规则都不排除它，读数比一般的 ok 读数略高。这样"只留 ok"一定会丢掉有效读数，算不对。
  - 错误路径表新增 E8（只留 ok）和 E9（条件写反），都归为 filter_error。出题时的区分度检查自动覆盖这两条：哪条算出的答案离正确答案不够远，就换一组数据重新出。
  - 新增对抗测试：这两种写法在所有题上都必须判错，并且归因到 E8、E9；每份数据都有 recal 行，任何版本的规则都不排除它。
- 理由：捷径会让成功率虚高，而虚高的部分恰好来自没读规则，这正是要研究的技能。这是出题的问题，不是模型的问题，所以要修。
- 影响：题目重新生成，版本升到 gen-0.2.1。每道题的难度设置和 gen-0.2.0 一一对应，只是数据里多了 recal 行。校准没有在 gen-0.2.1 上重跑：这次改动只会让成功率更低，不影响基座的选择；基线直接在 gen-0.2.1 上跑，同时起复核作用。到此冻结，之后不再修改考场，再发现的问题记入局限性。
